## 0. Σκεπτικό σχεδίασης — γιατί ακριβώς αυτοί οι τρεις αλγόριθμοι

Το ζητούμενο της εκφώνησης είναι να περιγραφούν **τρεις διαφορετικοί αλγόριθμοι** πολλαπλασιασμού
πίνακα × πίνακα (GEMM, *General Matrix–Matrix Multiplication*, $C = A\cdot B$) οι οποίοι **βασίζονται
στην αρχιτεκτονική** των Διαγραμμάτων 1 και 2. Η κεντρική σχεδιαστική μας απόφαση είναι ότι οι τρεις
αλγόριθμοι **δεν** είναι τρεις αυθαίρετες παραλλαγές, αλλά **τρία διαδοχικά σκαλιά αξιοποίησης της
ιεραρχίας μνήμης** της GPU:

| # | Αλγόριθμος | Επίπεδο μνήμης που εκμεταλλεύεται | Αρχείο κώδικα |
|---|---|---|---|
| 1 | **Naive** | μόνο **Global Memory** | `gemm_naive.cu` |
| 2 | **Tiled / Blocked** | **Shared Memory** (+ Global) | `gemm_tiled.cu` |
| 3 | **Register Blocking** | **Registers + Shared Memory** (+ Global) | `gemm_register.cu` |

Η λογική αυτή απορρέει **άμεσα** από το Διάγραμμα 1: η αρχιτεκτονική του Streaming Multiprocessor (SM)
εκθέτει τρία προγραμματιστικά αξιοποιήσιμα επίπεδα μνήμης με ραγδαία διαφορετικό κόστος πρόσβασης
(Global → Shared → Registers). Κάθε αλγόριθμος «κατεβαίνει» ένα σκαλί βαθύτερα σε αυτή την ιεραρχία,
μετατρέποντας ακριβές προσβάσεις στη Global Memory σε φθηνές επαναχρησιμοποιήσεις από Shared Memory
και Registers. Όπως θα δείξουμε ποσοτικά, αυτό αυξάνει το **arithmetic intensity** και, μέσω του
μοντέλου Roofline, μετατοπίζει το σημείο συμφόρησης (bottleneck) από το **εύρος ζώνης μνήμης** προς την
**υπολογιστική ισχύ** — που είναι ακριβώς ο στόχος κάθε βελτιστοποίησης σε GPU.

Ως **σημείο αναφοράς (gold standard)** χρησιμοποιείται η βιβλιοθήκη **cuBLAS** της NVIDIA (§6).

## 1. Η αρχιτεκτονική-στόχος (Διαγράμματα 1 & 2)

### 1.1 Διάγραμμα 1 — Εσωτερική δομή του υλικού (SP → SM → ιεραρχία μνήμης)

Το Διάγραμμα 1 περιγράφει την **εσωτερική ιεραρχία υπολογισμού και μνήμης** μιας NVIDIA GPU:

- **SP (Streaming Processor / CUDA core):** η στοιχειώδης αριθμητική μονάδα. Περιέχει μονάδες
  ακεραίων και κινητής υποδιαστολής και εκτελεί κατά βάση μία πράξη **FMA** (*Fused Multiply–Add*,
  $a \leftarrow a + b\cdot c$, δηλαδή 2 FLOP) ανά κύκλο. Είναι το «SP» των κουτιών του Διαγράμματος 1.
- **SM (Streaming Multiprocessor):** ομαδοποιεί πολλά SP μαζί με τους **κοινούς πόρους** που φαίνονται
  στο διάγραμμα:
  - τις **μονάδες ελέγχου** (*Control* — οι warp schedulers/dispatch units),
  - το **αρχείο καταχωρητών** (*register file*, 65.536 καταχωρητές των 32-bit ανά SM σε Turing/Ampere),
  - τη **Shared Memory** (το κάτω κουτί κάθε SM στο διάγραμμα).
  Το SM είναι η φυσική μονάδα που εκτελεί ένα ή περισσότερα **blocks** νημάτων.
- **L2 Cache:** κοινή cache **όλων** των SM, ενδιάμεσος σταθμός προς τη Global Memory.
- **Global Memory (DRAM/GDDR/HBM):** η κύρια μνήμη της συσκευής· μεγάλη χωρητικότητα, μεγάλο εύρος
  ζώνης, αλλά **πολύ μεγάλος λανθάνων χρόνος** (latency).

Η ιεραρχία αυτή είναι το θεμέλιο όλης της ανάλυσης που ακολουθεί: όσο ανεβαίνουμε (Global → L2 →
Shared → Registers) ο λανθάνων χρόνος **μικραίνει κατά τάξεις μεγέθους**, αλλά μικραίνει και η
χωρητικότητα και αλλάζει η εμβέλεια ορατότητας.

### 1.2 Το εκτελεστικό μοντέλο SIMT και τα warps

Το ότι τα SP ενός SM **μοιράζονται κοινές μονάδες ελέγχου** (κουτιά *Control* στο Διάγραμμα 1) έχει
άμεση συνέπεια στο εκτελεστικό μοντέλο: η GPU εκτελεί κατά **SIMT** (*Single Instruction, Multiple
Threads*). Συγκεκριμένα:

- Τα νήματα ομαδοποιούνται σε **warps των 32 νημάτων**. Ένα warp είναι η **ατομική μονάδα
  χρονοδρομολόγησης** του υλικού: σε κάθε έκδοση εντολής, ο scheduler εκδίδει **μία** εντολή που
  εκτελείται **ταυτόχρονα** και από τα 32 νήματα του warp (σε lockstep), το καθένα πάνω στα δικά του
  δεδομένα.
- **Warp divergence:** αν τα νήματα ενός warp πάρουν διαφορετικό κλάδο σε ένα `if`, οι κλάδοι
  **σειριοποιούνται** (εκτελείται πρώτα ο ένας με τα υπόλοιπα νήματα ανενεργά, μετά ο άλλος), με
  απώλεια απόδοσης. Γι' αυτό οι έλεγχοι ορίων στους kernels μας είναι σχεδιασμένοι ώστε να μη
  διασπούν τα warps στο «εσωτερικό» του πίνακα (διασπούν μόνο τα warps στις άκρες).
- **Latency hiding (απόκρυψη λανθάνοντος χρόνου):** ο τρόπος που η GPU κρύβει το τεράστιο latency της
  Global Memory δεν είναι οι caches (όπως στη CPU) αλλά η **υπερ-στράτευση** (oversubscription): κάθε
  SM κρατά ταυτόχρονα πολλά **έτοιμα** warps και, όταν ένα warp μπλοκάρει περιμένοντας μνήμη, ο
  scheduler αλλάζει αμέσως (με μηδενικό κόστος) σε άλλο έτοιμο warp. Η μετρική που εκφράζει «πόσα
  warps είναι ταυτόχρονα ενεργά ανά SM σε σχέση με το μέγιστο» λέγεται **occupancy** και θα την
  χρησιμοποιήσουμε επανειλημμένα παρακάτω.

### 1.3 Διάγραμμα 2 — Το μοντέλο Host / Device

Το Διάγραμμα 2 περιγράφει το **ετερογενές** μοντέλο εκτέλεσης:

- **Host** = CPU + Main Memory (κύρια μνήμη συστήματος).
- **Device** = η GPU, που περιέχει τα **SM** (Διάγραμμα 1) και τη δική της **Global Memory**.
- Τα δύο συνδέονται με τον δίαυλο **PCIe**.

Η ροή ενός υπολογισμού CUDA είναι:

```
1. cudaMalloc      : δέσμευση χώρου A, B, C στη Global Memory του device
2. cudaMemcpy H2D  : αντιγραφή A, B  Host → Device   (πάνω από PCIe)
3. kernel launch   : εκτέλεση του υπολογισμού στα SM
4. cudaMemcpy D2H  : αντιγραφή του αποτελέσματος C  Device → Host
```

Η μεταφορά μέσω PCIe (βήματα 2, 4) είναι **πολύ αργή** σε σχέση με το εσωτερικό εύρος ζώνης της GPU
(τυπικά ~16–32 GB/s PCIe έναντι 320–600+ GB/s στην ίδια τη μνήμη της συσκευής). Γι' αυτόν τον λόγο,
στη μεθοδολογία μέτρησης (Παραδοτέο ΙΙ/ΙΙΙ) χρονομετράμε **χωριστά** τον καθαρό υπολογισμό (kernel) και
το end-to-end (μαζί με τις μεταφορές): η σύγκριση των αλγορίθμων ως προς την **ποιότητα της λύσης**
γίνεται στον kernel, ενώ το PCIe είναι κοινός, σταθερός «φόρος» που εξαρτάται μόνο από το μέγεθος των
δεδομένων, όχι από τον αλγόριθμο.

### 1.4 Αντιστοίχιση της λογικής ιεραρχίας CUDA στο υλικό

Το προγραμματιστικό μοντέλο CUDA εκθέτει μια **λογική** ιεραρχία νημάτων που αντιστοιχίζεται απευθείας
στη **φυσική** ιεραρχία των Διαγραμμάτων 1 & 2:

| Λογική οντότητα CUDA | Φυσική μονάδα υλικού | Ιδιωτική μνήμη |
|---|---|---|
| **thread** (νήμα) | εκτελείται σε ένα **SP** | Registers (ιδιωτικοί) |
| **block** (ομάδα νημάτων) | δρομολογείται σε **ένα SM** | Shared Memory (κοινή στο block) |
| **grid** (όλα τα blocks του kernel) | καταλαμβάνει **όλη τη GPU** | Global Memory (κοινή σε όλους) |
| **warp** (32 νήματα) | μονάδα **χρονοδρομολόγησης** του SM | — |

Αυτή η αντιστοίχιση είναι ο «μοχλός» σχεδίασης: επιλέγοντας **διαστάσεις block** και **πόση δουλειά
αναλαμβάνει κάθε νήμα**, ο προγραμματιστής ελέγχει άμεσα ποια επίπεδα μνήμης χρησιμοποιούνται και πόσο
καλά «γεμίζει» το υλικό. Οι τρεις αλγόριθμοί μας διαφέρουν ακριβώς σε αυτές τις επιλογές.

### 1.5 Η ιεραρχία μνήμης ποσοτικά — η ρίζα του προβλήματος

| Μνήμη | Εμβέλεια (scope) | Λανθάνων χρόνος | Τυπικό μέγεθος | Ποιος τη διαχειρίζεται |
|---|---|---|---|---|
| **Registers** | ανά νήμα | ~1 κύκλος | 64K καταχωρητές 32-bit / SM | ο **μεταγλωττιστής** |
| **Shared Memory / L1** | ανά block (μέσα στο SM) | ~20–30 κύκλοι | ~48–164 KB / SM | ο **προγραμματιστής** |
| **L2 Cache** | όλα τα SM | ~200 κύκλοι | μερικά MB | το υλικό (αυτόματα) |
| **Global Memory** (DRAM) | όλη η GPU + host | ~400–800 κύκλοι | GB | το υλικό (αυτόματα) |

Η κρίσιμη παρατήρηση: μια πρόσβαση στη **Global Memory είναι ~20–40× ακριβότερη** από μια πρόσβαση στη
Shared Memory και **~400–800× ακριβότερη** από έναν καταχωρητή. Επιπλέον, η Global Memory έχει
**πεπερασμένο εύρος ζώνης** (π.χ. ~320 GB/s στο T4, ~608 GB/s στην RTX 3070 Ti). Άρα, αν ένας
αλγόριθμος διαβάζει «πολλά bytes ανά πράξη», θα φραχτεί από αυτό το εύρος ζώνης ανεξάρτητα από το πόση
υπολογιστική ισχύ διαθέτει η GPU.

**Όλη η τέχνη της βελτιστοποίησης του GEMM συνοψίζεται σε μία πρόταση:** *φέρε κάθε δεδομένο μία φορά από
τη Global Memory και επαναχρησιμοποίησέ το όσο το δυνατόν περισσότερες φορές από τη Shared Memory και
τους Registers.* Αυτό ακριβώς ποσοτικοποιεί η έννοια του arithmetic intensity (§2.2).

## 2. Θεωρητικό υπόβαθρο: γιατί ο GEMM «ταιριάζει» στη GPU

### 2.1 Ορισμός και πολυπλοκότητα

Για $C = A\cdot B$ με $A \in \mathbb{R}^{M\times K}$, $B \in \mathbb{R}^{K\times N}$, $C \in \mathbb{R}^{M\times N}$:

$$ C_{ij} = \sum_{k=0}^{K-1} A_{ik}\,B_{kj} $$

- **Υπολογιστικός φόρτος:** για κάθε ένα από τα $M\cdot N$ στοιχεία εξόδου εκτελούμε $K$ πολλαπλασιασμούς
  και $K$ προσθέσεις, δηλαδή συνολικά
  $$ \text{FLOP} = 2\,M\,N\,K \quad\big(\text{για τετράγωνους:}~2N^3\big). $$
- **Όγκος δεδομένων:** $M\!\cdot\!K + K\!\cdot\!N + M\!\cdot\!N$ στοιχεία, δηλαδή $\Theta(N^2)$ για
  τετράγωνους πίνακες.

Η καθοριστική σχέση είναι ότι ο **υπολογισμός είναι $\Theta(N^3)$ ενώ τα δεδομένα είναι $\Theta(N^2)$**.
Ο λόγος τους είναι $\Theta(N)$: **κάθε στοιχείο μπορεί, θεωρητικά, να επαναχρησιμοποιηθεί έως $N$ φορές.**
Αυτή η εγγενής δυνατότητα επαναχρησιμοποίησης είναι που κάνει τον GEMM ιδανικό υποψήφιο για την ιεραρχία
μνήμης της GPU — και είναι ο λόγος που οι τρεις αλγόριθμοι, που διαφέρουν *μόνο* στο πόσο εκμεταλλεύονται
αυτή την επαναχρησιμοποίηση, δίνουν ριζικά διαφορετικές επιδόσεις.

### 2.2 Arithmetic Intensity και το μοντέλο Roofline

Ορίζουμε το **arithmetic intensity** (αριθμητική ένταση) ως:

$$ AI = \frac{\text{FLOP που εκτελούνται}}{\text{bytes που διακινούνται από/προς ένα επίπεδο μνήμης}} \quad [\text{flop/byte}] $$

Το μοντέλο **Roofline** συνδέει το $AI$ με την επιτεύξιμη απόδοση. Η μέγιστη απόδοση ενός kernel φράσσεται
από το **ελάχιστο** δύο οριζόντων:

$$ P_{\max} = \min\big(\underbrace{P_{\text{peak}}}_{\text{όριο υπολογισμού}},\; \underbrace{AI \times B_{\text{mem}}}_{\text{όριο εύρους ζώνης}}\big) $$

όπου $P_{\text{peak}}$ η κορυφαία υπολογιστική ισχύς (FLOP/s) και $B_{\text{mem}}$ το εύρος ζώνης μνήμης
(byte/s). Το **ridge point** (σημείο καμπής) είναι το $AI$ στο οποίο τα δύο όρια συναντώνται:

$$ AI_{\text{ridge}} = \frac{P_{\text{peak}}}{B_{\text{mem}}} $$

- Αν $AI < AI_{\text{ridge}}$ → ο kernel είναι **memory-bound** (τον φράζει το εύρος ζώνης).
- Αν $AI > AI_{\text{ridge}}$ → ο kernel είναι **compute-bound** (τον φράζει η αριθμητική ισχύς — το επιθυμητό).

### 2.3 Τα ridge points των δύο αρχιτεκτονικών της μελέτης

Από τις **προδιαγραφές** (όχι από μετρήσεις — ανήκουν εδώ, στο αρχιτεκτονικό μέρος):

| GPU | $P_{\text{peak}}$ (FP32) | $B_{\text{mem}}$ | $AI_{\text{ridge}} = P/B$ |
|---|---|---|---|
| NVIDIA **T4** (Turing) | ~8,1 TFLOPS | ~320 GB/s | **~25 flop/byte** |
| RTX **3070 Ti** (Ampere) | ~21,7 TFLOPS | ~608 GB/s | **~36 flop/byte** |

Με άλλα λόγια: για να γίνει ένας kernel **compute-bound** σε αυτές τις GPU πρέπει να εκτελεί
**πάνω από ~25–36 FLOP για κάθε byte** που διαβάζει από τη Global Memory. Κρατήστε αυτούς τους αριθμούς:
θα δείξουμε ότι ο naive (§3) έχει $AI = 0{,}25$, ο tiled (§4) $AI = 4$ και ο register blocking (§5)
$AI = 16$ (στο επίπεδο Global) — δηλαδή ο καθένας **πλησιάζει** προοδευτικά το ridge point, χωρίς όμως ο
απλός αυτός υπολογισμός να το περνά. Η εξήγηση γιατί στην πράξη ο register blocking γίνεται σχεδόν
compute-bound (ενώ ο global-only υπολογισμός δίνει 16 < 25) βρίσκεται στην **L2 cache** και στη
**δεύτερη roofline του επιπέδου Shared/Registers** — και είναι ένα από τα βασικά επιστημονικά σημεία
αυτής της εργασίας (§5.4).

## 3. Αλγόριθμος 1 — Naive (μόνο Global Memory)

### 3.1 Ιδέα και αντιστοίχιση στην αρχιτεκτονική

Η πιο άμεση μετάφραση του μαθηματικού ορισμού: **ένα νήμα ανά στοιχείο εξόδου**. Το νήμα $(row, col)$
διαβάζει ολόκληρη τη γραμμή $row$ του $A$ και ολόκληρη τη στήλη $col$ του $B$ **απευθείας από τη Global
Memory** και υπολογίζει το $C_{row,col}$. Χρησιμοποιεί **μόνο το κατώτατο επίπεδο** της ιεραρχίας του
Διαγράμματος 1.

```cuda
__global__ void mm_naive(int M,int N,int K,const float*A,const float*B,float*C){
    int row = blockIdx.y*blockDim.y + threadIdx.y;
    int col = blockIdx.x*blockDim.x + threadIdx.x;
    if (row < M && col < N) {
        float sum = 0.0f;
        for (int k = 0; k < K; ++k)
            sum += A[row*K + k] * B[k*N + col];   // 2 FLOP, 2 global reads ανά k
        C[row*N + col] = sum;
    }
}
```

Διαμόρφωση εκτέλεσης: `block(16,16)` = 256 νήματα/block (8 warps), `grid` που καλύπτει όλο το $M\times N$.

### 3.2 Ανάλυση arithmetic intensity

Στον εσωτερικό βρόχο, σε κάθε επανάληψη $k$:
- εκτελούνται **2 FLOP** (ένας πολλαπλασιασμός + μία πρόσθεση),
- διαβάζονται **2 στοιχεία** από τη Global Memory ($A_{row,k}$ και $B_{k,col}$) = $2\times4 = 8$ bytes.

$$ AI_{\text{naive}} = \frac{2~\text{FLOP}}{8~\text{bytes}} = 0{,}25~\text{flop/byte} $$

Είναι **σταθερό, ανεξάρτητο του μεγέθους** του προβλήματος, και **εκατονταπλάσια μικρότερο** από το
ridge point (~25–36). Άρα ο naive είναι, θεωρητικά, **βαθιά memory-bound**: το προβλεπόμενο όριο
απόδοσης είναι μόλις $0{,}25 \times 320~\text{GB/s} \approx 80$ GFLOPS στο T4 — δηλαδή ~1% της κορυφαίας
υπολογιστικής ισχύος. Αντίστοιχα, ο **συνολικός όγκος** προσβάσεων στη Global Memory είναι $\Theta(N^3)$
(κάθε ένα από τα $N^2$ νήματα διαβάζει $2K$ στοιχεία): καμία επαναχρησιμοποίηση δεν αξιοποιείται ρητά.

### 3.3 Πρότυπα πρόσβασης: coalescing και broadcast

Παρότι «αφελής», ο kernel έχει σωστό **πρότυπο πρόσβασης**, χάρη στην αντιστοίχιση `threadIdx.x → col`:

- **Πρόσβαση στον $B$** (`B[k*N+col]`): τα γειτονικά νήματα ενός warp (διαδοχικό `col`) διαβάζουν
  **διαδοχικές διευθύνσεις** → **coalesced** πρόσβαση: το υλικό συγχωνεύει τις 32 αιτήσεις σε λίγες
  συναλλαγές μνήμης των 128 bytes, αξιοποιώντας πλήρως το εύρος ζώνης.
- **Πρόσβαση στον $A$** (`A[row*K+k]`): όλα τα νήματα ενός (μισού) warp έχουν **ίδιο** `row` και `k` →
  διαβάζουν την **ίδια** διεύθυνση → **broadcast** (μία ανάγνωση εξυπηρετεί όλο το warp).

### 3.4 Ο κρυφός ρόλος της L2 cache — γιατί στην πράξη ξεπερνά το θεωρητικό όριο

Αν και το «χάρτινο» $AI = 0{,}25$ προβλέπει ~80 GFLOPS, στην πράξη ο naive πιάνει αρκετές εκατοντάδες
GFLOPS. Ο λόγος είναι η **L2 cache** (Διάγραμμα 1): όταν γειτονικά blocks ξαναζητούν τις **ίδιες**
γραμμές του $A$ και στήλες του $B$, αυτές βρίσκονται ήδη στην L2 και **δεν** ξαναδιαβάζονται από τη
DRAM. Έτσι η *πραγματική* κίνηση προς τη DRAM είναι μικρότερη από τη «χάρτινη», και το *effective* $AI$
είναι υψηλότερο. Αυτό είναι το πρώτο μάθημα της εργασίας: **η ιεραρχία μνήμης δουλεύει και «από μόνη
της» (μέσω caches), αλλά τυχαία και ανεξέλεγκτα**· οι επόμενοι αλγόριθμοι την κάνουν να δουλεύει
**ελεγχόμενα** (μέσω Shared Memory που διαχειρίζεται ο προγραμματιστής).

### 3.5 Πλεονεκτήματα / Μειονεκτήματα (αρχιτεκτονικά)

- **+** Απλούστατος, εύκολος στην επαλήθευση· σωστό coalescing· υψηλό occupancy (ελάχιστοι καταχωρητές
  και μηδενική Shared Memory ανά block → πολλά ταυτόχρονα warps για latency hiding).
- **−** Μηδενική **ρητή** επαναχρησιμοποίηση → σπατάλη εύρους ζώνης → memory-bound → η πιο αργή λύση.
  Είναι το **baseline** πάνω στο οποίο μετριέται κάθε βελτιστοποίηση.

## 4. Αλγόριθμος 2 — Tiled / Blocked (Shared Memory)

### 4.1 Ιδέα και αντιστοίχιση στην αρχιτεκτονική

Η αδυναμία του naive είναι ότι κάθε δεδομένο ξαναδιαβάζεται από τη Global Memory. Η λύση εκμεταλλεύεται
τη **Shared Memory** του SM (Διάγραμμα 1) ως **διαχειριζόμενη από τον προγραμματιστή cache**: τα νήματα
ενός block **συνεργάζονται** ώστε να φέρουν μία φορά υπο-πίνακες (tiles) $TILE\times TILE$ των $A, B$ στη
Shared Memory και να τους **επαναχρησιμοποιήσουν** πολλές φορές.

```cuda
template<int TILE> __global__ void mm_tiled(int M,int N,int K, ...){
    __shared__ float As[TILE][TILE], Bs[TILE][TILE];
    float sum = 0.0f;
    for (int t = 0; t < (K+TILE-1)/TILE; ++t) {
        As[ty][tx] = (έλεγχος ορίων) ? A[row*K + (t*TILE+tx)] : 0.0f;  // φόρτωση tile A
        Bs[ty][tx] = (έλεγχος ορίων) ? B[(t*TILE+ty)*N + col] : 0.0f;  // φόρτωση tile B
        __syncthreads();                          // (1) φράγμα: γέμισαν όλα τα νήματα
        #pragma unroll
        for (int k = 0; k < TILE; ++k)
            sum += As[ty][k] * Bs[k][tx];         // υπολογισμός ΑΠΟ Shared Memory
        __syncthreads();                          // (2) φράγμα: πριν ξαναγραφτούν τα tiles
    }
    if (row < M && col < N) C[row*N + col] = sum;
}
```

Χρησιμοποιούμε `TILE = 16` → `block(16,16)` = 256 νήματα (8 warps). Κάθε νήμα εξακολουθεί να υπολογίζει
**ένα** στοιχείο, αλλά τώρα διαβάζοντας από τη Shared Memory αντί από τη Global.

### 4.2 Ο ρόλος του `__syncthreads()` — συνέπεια του μοντέλου block/SM

Επειδή το block εκτελείται σε **ένα SM** και η Shared Memory είναι **κοινή** στο block, χρειάζονται δύο
φράγματα συγχρονισμού ανά επανάληψη:
1. μετά τη φόρτωση, ώστε **κανένα** νήμα να μην αρχίσει υπολογισμό πριν **όλα** τα νήματα γεμίσουν το
   tile (αλλιώς διαβάζει «σκουπίδια»),
2. μετά τον υπολογισμό, ώστε κανένα νήμα να μην **ξαναγράψει** το tile της επόμενης επανάληψης ενώ
   κάποιο άλλο ακόμη διαβάζει το τρέχον.
Είναι το τίμημα της συνεργασίας: ένα μικρό κόστος συγχρονισμού με αντάλλαγμα τεράστια μείωση της κίνησης
μνήμης.

### 4.3 Ανάλυση arithmetic intensity — βελτίωση κατά παράγοντα TILE

**Κλειδί:** κάθε στοιχείο φορτώνεται **μία φορά** από τη Global Memory στη Shared Memory και
χρησιμοποιείται **TILE φορές** από εκεί (μία για κάθε γραμμή/στήλη του αντίστοιχου tile). Ποσοτικά, για
τετράγωνο $N$, ο συνολικός αριθμός φορτώσεων από τη Global γίνεται:

$$ \text{global reads} = \underbrace{(N/TILE)^2}_{\text{output tiles}} \times \underbrace{(N/TILE)}_{\text{k-steps}} \times \underbrace{2\,TILE^2}_{\text{στοιχεία }A,B\text{ ανά step}} = \frac{2N^3}{TILE} $$

Άρα, σε σχέση με τον naive (που κάνει $2N^3$ προσβάσεις), η κίνηση Global **μειώνεται ακριβώς κατά
παράγοντα TILE**. Το arithmetic intensity στο επίπεδο Global γίνεται:

$$ AI_{\text{tiled}} = \frac{2N^3~\text{FLOP}}{(2N^3/TILE)\cdot 4~\text{bytes}} = \frac{TILE}{4} \xrightarrow{TILE=16} 4~\text{flop/byte} $$

δηλαδή **16× υψηλότερο** από τον naive (0,25 → 4). Παραμένει κάτω από το ridge point (~25–36), οπότε ο
tiled είναι ακόμη memory-bound, αλλά **πολύ λιγότερο**.

### 4.4 Το επόμενο bottleneck: η ίδια η Shared Memory

Γιατί ο tiled δεν φτάνει το ridge point αν και μειώνει τόσο την κίνηση Global; Γιατί μετατοπίζει το
bottleneck **ένα επίπεδο πιο πάνω**, στην ίδια τη Shared Memory. Στον εσωτερικό βρόχο, κάθε νήμα κάνει
**2 αναγνώσεις Shared** (`As[ty][k]`, `Bs[k][tx]`) για να παραγάγει **1 FMA** (2 FLOP):

$$ AI^{\text{shared}}_{\text{tiled}} = \frac{2~\text{FLOP}}{2\cdot 4~\text{bytes}} = 0{,}25~\text{flop/byte (στο επίπεδο Shared)} $$

Δηλαδή ο tiled, ενώ έλυσε το πρόβλημα της Global, είναι τώρα **shared-memory-bound**: «σπαταλά» μία
ανάγνωση Shared ανά μισή πράξη. Αυτό ακριβώς θεραπεύει ο τρίτος αλγόριθμος.

### 4.5 Διαχείριση ορίων, bank conflicts, occupancy

- **Όρια (boundary handling):** για διαστάσεις που δεν είναι ακέραια πολλαπλάσια του TILE, οι θέσεις
  εκτός πίνακα γεμίζονται με **0.0** κατά τη φόρτωση (βλ. ternary στον κώδικα), ώστε να μη χρειάζονται
  ειδικές περιπτώσεις στον υπολογισμό και να μη διασπώνται τα warps του εσωτερικού. Έτσι ο kernel είναι
  **γενικός** για κάθε $M, N, K$.
- **Bank conflicts:** η Shared Memory είναι οργανωμένη σε **32 banks**. Στο `Bs[k][tx]` τα νήματα ενός
  warp (διαδοχικό `tx`) προσπελαύνουν **διαφορετικά banks** → χωρίς conflict· στο `As[ty][k]` (κοινό
  `k`) η ανάγνωση είναι **broadcast** → χωρίς conflict. Το πρότυπο είναι, επομένως, ευνοϊκό.
- **Occupancy:** η χρήση Shared είναι μικρή ($2\cdot 16^2\cdot 4 = 2$ KB/block) → επιτρέπει πολλά
  ταυτόχρονα blocks ανά SM → καλό occupancy και latency hiding.

### 4.6 Πλεονεκτήματα / Μειονεκτήματα

- **+** Δραστική μείωση κίνησης Global (×TILE)· σχετικά απλός κώδικας· καλή ισορροπία
  απόδοσης/πολυπλοκότητας· πλήρως γενικός (όρια + ορθογώνιοι πίνακες).
- **−** Κάθε νήμα υπολογίζει ακόμη **ένα** στοιχείο → γίνεται **shared-memory-bound** (§4.4)· η απόδοση
  εξαρτάται από την επιλογή του TILE και είναι ευαίσθητη σε bank conflicts σε άλλα πρότυπα πρόσβασης.

## 5. Αλγόριθμος 3 — Register Blocking / Thread Coarsening (Shared + Registers)

### 5.1 Ιδέα και αντιστοίχιση στην αρχιτεκτονική

Ο τρίτος αλγόριθμος προσθέτει το **τελευταίο και ταχύτερο** επίπεδο της ιεραρχίας: τους **Registers**.
Υλοποιεί **διπλό tiling (two-level blocking)** συνδυασμένο με **thread coarsening** (κάθε νήμα κάνει
περισσότερη δουλειά):

- Σε επίπεδο **block**: όπως ο tiled, κάθε block υπολογίζει ένα μπλοκ $BM\times BN$ της εξόδου, φέρνοντας
  φέτες $A$ ($BM\times BK$) και $B$ ($BK\times BN$) στη Shared Memory.
- Σε επίπεδο **νήματος**: σε αντίθεση με τον tiled, κάθε νήμα δεν υπολογίζει 1 στοιχείο αλλά ένα
  **υπο-μπλοκ $TM\times TN$** στοιχείων, κρατώντας τους $TM\cdot TN$ **συσσωρευτές σε καταχωρητές**.

```cuda
template<int BM,int BN,int BK,int TM,int TN>
__global__ void mm_register(int M,int N,int K, ...){
    __shared__ float As[BM*BK], Bs[BK*BN];
    float acc[TM*TN] = {0.0f};        // ΣΥΣΣΩΡΕΥΤΕΣ ΣΤΟΥΣ REGISTERS
    float regM[TM], regN[TN];
    for (int bk = 0; bk < K; bk += BK) {
        // συνεργατική φόρτωση των tiles A, B στη Shared (με έλεγχο ορίων)
        ... As[...] = ... ;  Bs[...] = ... ;
        __syncthreads();
        #pragma unroll
        for (int k = 0; k < BK; ++k) {
            for (int i=0;i<TM;++i) regM[i] = As[(threadRow*TM+i)*BK + k]; // Shared→Reg
            for (int j=0;j<TN;++j) regN[j] = Bs[k*BN + threadCol*TN + j]; // Shared→Reg
            for (int i=0;i<TM;++i)               // ΕΞΩΤΕΡΙΚΟ ΓΙΝΟΜΕΝΟ (outer product)
              for (int j=0;j<TN;++j)
                acc[i*TN+j] += regM[i]*regN[j];  // TM*TN FMA από registers
        }
        __syncthreads();
    }
    // εγγραφή των TM*TN αποτελεσμάτων (με έλεγχο ορίων)
}
```

**Προεπιλεγμένες παράμετροι:** `BM=BN=64, BK=8, TM=TN=8`. Συνέπειες:
- `blockDim = (BN/TN, BM/TM) = (8,8)` → **64 νήματα/block** (2 warps),
- κάθε νήμα παράγει $TM\cdot TN = 8\times8 =$ **64 αποτελέσματα**,
- Shared Memory/block $= (BM\!\cdot\!BK + BK\!\cdot\!BN)\cdot 4 = (512+512)\cdot4 = 4$ KB.

### 5.2 Το «κόλπο» του εξωτερικού γινομένου (outer product)

Αυτή είναι η καρδιά του αλγορίθμου. Σε κάθε βήμα $k$, το νήμα φορτώνει $TM$ τιμές του $A$ (`regM`) και
$TN$ τιμές του $B$ (`regN`) **από τη Shared στους Registers**, και κατόπιν παράγει **όλους** τους
$TM\times TN$ συνδυασμούς γινομένων. Το κρίσιμο: **μία** τιμή `regM[i]` (ένα στοιχείο του $A$)
χρησιμοποιείται σε $TN$ πολλαπλασιασμούς, και **μία** τιμή `regN[j]` σε $TM$ πολλαπλασιασμούς.
Δηλαδή κάθε ανάγνωση από τη Shared «τροφοδοτεί» πολλές πράξεις — αντί για μία, όπως στον tiled.

### 5.3 Ανάλυση arithmetic intensity — σε δύο επίπεδα

**(α) Επίπεδο Global.** Όπως στον tiled, η κίνηση Global καθορίζεται από το μέγεθος του **block tile**.
Για τετράγωνο $N$:

$$ AI^{\text{global}}_{\text{reg}} = \frac{1}{2\left(\tfrac{1}{BM}+\tfrac{1}{BN}\right)} = \frac{BM\cdot BN}{2(BM+BN)} \xrightarrow{BM=BN=64} \frac{64}{4} = 16~\text{flop/byte} $$

δηλαδή **64× καλύτερο από τον naive** και **4× καλύτερο από τον tiled (TILE=16)** — αποτέλεσμα του
μεγαλύτερου tile $64$ έναντι $16$.

**(β) Επίπεδο Shared.** Εδώ φαίνεται το πραγματικό κέρδος του register blocking. Σε κάθε βήμα $k$ το νήμα
κάνει $TM+TN$ αναγνώσεις Shared και παράγει $TM\cdot TN$ FMA ($2\,TM\,TN$ FLOP):

$$ AI^{\text{shared}}_{\text{reg}} = \frac{2\,TM\,TN}{(TM+TN)\cdot 4} = \frac{TM\,TN}{2(TM+TN)} \xrightarrow{TM=TN=8} \frac{64}{32} = 2~\text{flop/byte} $$

Σύγκριση με τον tiled ($AI^{\text{shared}}=0{,}25$): ο register blocking κάνει **$2 / 0{,}25 = 8\times$
λιγότερες προσβάσεις Shared ανά πράξη**. Έτσι **αποφορτίζει τη Shared Memory** (το bottleneck του tiled)
και μετατοπίζει το όριο προς την **καθαρή υπολογιστική ισχύ (FMA pipeline)** — δηλαδή προς το επιθυμητό
compute-bound καθεστώς.

### 5.4 Γιατί γίνεται σχεδόν compute-bound παρότι $AI^{\text{global}}=16 < 25$

Παρατηρήσαμε ότι ακόμη και το $AI^{\text{global}}=16$ είναι κάτω από το ridge point (~25–36). Πώς τότε ο
register blocking πλησιάζει τη συμπεριφορά βιβλιοθήκης; Δύο λόγοι, και οι δύο αρχιτεκτονικοί:

1. **L2 cache:** τα block tiles $64\times64$ που μοιράζονται γειτονικά blocks επαναχρησιμοποιούνται μέσω
   της L2, μειώνοντας την *πραγματική* κίνηση DRAM κάτω από τη «χάρτινη» → το *effective* global $AI$
   ανεβαίνει πάνω από το ridge point.
2. **Roofline σε πολλά επίπεδα:** το «χάρτινο» δίτιμο μοντέλο (DRAM vs compute) είναι υπεραπλουστευμένο.
   Στην πραγματικότητα υπάρχουν **διαδοχικές roofline** (DRAM → L2 → Shared → Registers). Ο naive
   φράσσεται στην πρώτη, ο tiled στη Shared, και ο register blocking μετατοπίζεται αρκετά ώστε να τον
   φράσσει η **έκδοση εντολών FMA** — δηλαδή η ίδια η υπολογιστική ικανότητα του SM.

### 5.5 Register pressure, occupancy και ο ρόλος του ILP

Το τίμημα είναι η **πίεση καταχωρητών (register pressure)**: κάθε νήμα χρειάζεται τουλάχιστον
$TM\!\cdot\!TN = 64$ καταχωρητές μόνο για τους συσσωρευτές `acc`, συν `regM`, `regN`, δείκτες κ.λπ.
(τυπικά ~100+ καταχωρητές/νήμα). Με 65.536 καταχωρητές/SM, αυτό **περιορίζει** τον αριθμό των ταυτόχρονων
νημάτων → **χαμηλό occupancy**.

Γιατί τότε είναι ο ταχύτερος; Λόγω της αρχής (Volkov): **το υψηλό occupancy δεν είναι αυτοσκοπός — είναι
απλώς ένας τρόπος να κρυφτεί το latency.** Ο register blocking κρύβει το latency με διαφορετικό τρόπο:
με **παραλληλισμό επιπέδου εντολής (ILP)**. Κάθε νήμα έχει 64 **ανεξάρτητους** συσσωρευτές που μπορούν να
«γεμίσουν» το pipeline FMA χωρίς εξαρτήσεις δεδομένων, ώστε ακόμη και με λίγα warps το SM να παραμένει
απασχολημένο. Έτσι ανταλλάσσει occupancy με ILP — και κερδίζει, αρκεί το πρόβλημα να είναι αρκετά μεγάλο
(βλ. §5.6).

### 5.6 Η αδυναμία στα μικρά προβλήματα

Τα μεγάλα tiles $64\times64$ σημαίνουν **λίγα blocks** για μικρά $N$. Π.χ. για $N=128$ προκύπτουν μόλις
$(128/64)^2 = 4$ blocks — ελάχιστα για να «γεμίσουν» τα 40–48 SM της GPU, που μένουν σε μεγάλο βαθμό
**αδρανή**. Επομένως, το θεωρητικό πλεονέκτημα του register blocking **εμφανίζεται μόνο σε αρκετά μεγάλη
κλίμακα** — μια πρόβλεψη που η εμπειρική ανάλυση (Παραδοτέο ΙΙΙ) επιβεβαιώνει.

### 5.7 Πλεονεκτήματα / Μειονεκτήματα

- **+** Υψηλότατο arithmetic intensity και στα δύο επίπεδα (Global & Shared)· αποφορτίζει τη Shared
  Memory (8× λιγότερες προσβάσεις/πράξη)· πλησιάζει τη συμπεριφορά πραγματικής βιβλιοθήκης· κρύβει
  latency μέσω ILP αντί για occupancy.
- **−** Υψηλή πίεση καταχωρητών → χαμηλό occupancy· πιο σύνθετος κώδικας· **κακή απόδοση σε μικρά
  προβλήματα** (overhead/υποαπασχόληση SM > όφελος).

## 6. Σημείο αναφοράς — cuBLAS

Ως «οροφή» επιδόσεων και ως αναφορά ορθότητας χρησιμοποιείται η **`cublasSgemm`** της NVIDIA. Είναι η
βιομηχανικά βελτιστοποιημένη υλοποίηση και ενσωματώνει **όλες** τις παραπάνω ιδέες σε ακραίο βαθμό, συν
επιπλέον τεχνικές: register/warp-level tiling, **double buffering** (επικάλυψη φόρτωσης επόμενου tile με
υπολογισμό τρέχοντος), **vectorized** φορτώσεις (`float4`), αυτόματη επιλογή kernel/heuristics ανά μέγεθος
και, σε νεότερες GPU, χρήση **Tensor Cores**. Συγκρίνοντας τους τρεις αλγορίθμους μας με τη cuBLAS,
μετράμε πόσο του διαθέσιμου «ταβανιού» κάθε αρχιτεκτονικής κατακτά η κάθε σχεδίαση.

> Τεχνική σημείωση: η cuBLAS είναι **column-major**, ενώ οι πίνακές μας είναι **row-major**. Την καλούμε
> με εναλλαγμένους τελεστές ώστε να υπολογίζει $C^{T} = B^{T}\cdot A^{T}$, που σε row-major διάταξη
> ισοδυναμεί ακριβώς με το ζητούμενο $C = A\cdot B$.

## 7. Συγκριτικός πίνακας των τριών αλγορίθμων (θεωρητική σύνοψη)

| Χαρακτηριστικό | **Naive** | **Tiled** (TILE=16) | **Register Blocking** (64/8/8) |
|---|---|---|---|
| Επίπεδα ιεραρχίας που αξιοποιεί | Global | Global → **Shared** | Global → Shared → **Registers** |
| Αποτελέσματα ανά νήμα | 1 | 1 | **64** ($TM\!\times\!TN$) |
| Νήματα ανά block | 256 | 256 | 64 |
| Shared Memory ανά block | 0 | 2 KB | 4 KB |
| $AI$ στο επίπεδο **Global** | **0,25** | **4** | **16** flop/byte |
| $AI$ στο επίπεδο **Shared** | — | 0,25 | **2** flop/byte |
| Παράγοντας μείωσης κίνησης Global vs naive | ×1 | **×16** | **×64** |
| Κύριο σημείο συμφόρησης (bottleneck) | DRAM bandwidth | Shared-memory bandwidth | FMA throughput / compute |
| Καθεστώς (έναντι ridge ~25–36) | βαθιά memory-bound | memory-bound | ~compute-bound (με L2) |
| Occupancy | υψηλό | υψηλό | χαμηλό (μεγάλη register pressure) |
| Μηχανισμός latency hiding | occupancy | occupancy | **ILP** |
| Πολυπλοκότητα κώδικα | ελάχιστη | μέτρια | υψηλή |
| Αναμενόμενη συμπεριφορά | σταθερά αργός | ~1,5–2× ταχύτερος | ταχύτερος σε **μεγάλα** $N$, αργός σε μικρά |

**Κεντρικό συμπέρασμα του Παραδοτέου Ι:** Οι τρεις αλγόριθμοι σχηματίζουν μια **μονοτονική κλίμακα**
αξιοποίησης της ιεραρχίας μνήμης του Διαγράμματος 1. Κάθε βήμα (Global → Shared → Registers)
**πολλαπλασιάζει το arithmetic intensity** και **μετατοπίζει το bottleneck** προς τα πάνω στη ιεραρχία —
από το εύρος ζώνης της DRAM (naive), στη Shared Memory (tiled), και τελικά στην καθαρή υπολογιστική ισχύ
(register blocking). Αυτή ακριβώς η διαδρομή είναι που ακολουθούν και οι πραγματικές βιβλιοθήκες υψηλής
απόδοσης (cuBLAS), και είναι η βάση για τις εφαρμογές Deep Learning και LLMs που αναφέρει η εκφώνηση.

## 8. Σύνδεση με τα επόμενα παραδοτέα (ελέγξιμες προβλέψεις)

Η παραπάνω αρχιτεκτονική ανάλυση παράγει συγκεκριμένες, **ελέγξιμες προβλέψεις**, οι οποίες
επαληθεύονται εμπειρικά στο Παραδοτέο ΙΙΙ:

1. Στα ρεαλιστικά μεγέθη ($N \ge 512$) η κατάταξη θα είναι **cuBLAS > Register > Tiled > Naive** (σειρά
   αύξουσας αξιοποίησης της ιεραρχίας μνήμης).
2. Ο **naive** θα έχει ~σταθερή απόδοση ανεξάρτητη του $N$ (υπογραφή memory-bound πυρήνα).
3. Ο **register blocking** θα είναι **αργός σε μικρά $N$** (υποαπασχόληση SM, §5.6) και **κυρίαρχος σε
   μεγάλα $N$** (όπου το υψηλό AI και το ILP αποδίδουν).
4. Η βέλτιστη στρατηγική θα **εξαρτάται από την αρχιτεκτονική** (διαφορετικά ridge points / L2 / αριθμός
   SM στο T4 έναντι της RTX 3070 Ti).

Έτσι το Παραδοτέο Ι δεν είναι απλώς περιγραφικό: θέτει τις **αρχιτεκτονικές υποθέσεις** που τα Παραδοτέα
ΙΙ (υλοποίηση) και ΙΙΙ (μέτρηση/ανάλυση) καλούνται να επιβεβαιώσουν.
